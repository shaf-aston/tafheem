# Plan: the security system (web, Android app, server)

Status: phase 1 shipped on branch `claude/confident-franklin-mzdz6f`. Phases 2 and 3 are staged here
and need the owner (secrets, server access, an identity decision).
Lifecycle: requirements → research → threat model → design (options scored) → plan → execute → verify → ship.
Team: lead (threat model, design, execution); **researcher** (primary sources, validated configs with
the real tools: `caddy validate`, `vercel build`, schema checks); **auditor** (read-only attack-surface
review of the code, then of every diff). Each finding below is labelled with its evidence.

## 1 · Requirements

The ask: very high-quality security and security logging, protection against "everything" (injections,
prompt injection, AI scrapers, abuse) on the web, the Android app and the server. Everything must be
done from a CLI, must keep the architecture maintainable, and must keep the app smooth and fast.

How each part is checked:

| # | Requirement | Testable condition | Check |
|---|---|---|---|
| R1 | Every refused or failed request is on record | One JSON line for every 401/403/405/413/415/422/429/5xx, with time, kind, request id, client address, method and route template. Account events (signup, login, unknown name, deletion, public toggle) write their own line | `tests/core/test_security_log.py` |
| R2 | The log is never a liability | No query text, body, key or header value. CR/LF and control bytes cannot forge or colour a line. Fields are capped and secrets scrubbed. A full disk never fails a request | same file: forged-line, control-character, scrub, unwritable-log tests |
| R3 | The log survives two processes and rotation | `WatchedFileHandler` plus system logrotate (daily, 90 days, gzip). A copy goes to journald | rotation test; `deploy/logrotate.conf` validated with real logrotate |
| R4 | A learner's error report can be traced | Every answer, including a crash 500, carries `X-Request-ID`, which matches its log line | `test_every_answer_carries_a_request_id`, `test_a_crash_answer_still_carries_its_id_and_is_inert` |
| R5 | An API answer can never run as a page | Every `/api` answer has nosniff, CSP `default-src 'none'; frame-ancestors 'none'`, no-referrer and CORP same-site. `/docs` is untouched | `tests/core/test_security_headers.py` |
| R6 | Per-learner answers are never kept by a shared cache | A request that names a learner, on a route that set no Cache-Control, is answered `private, no-store`. A day-long public cache on fixed data is kept | same file |
| R7 | Cross-site calls are as narrow as the app needs | CORS has no credentials, allows only the methods and headers the frontend sends, and exposes `X-Request-ID`. A test reads the frontend's own source, so a new header cannot be forgotten | same file |
| R8 | No route leaks other people's data | `/api/practice/kept` needs the sentence. The username list is off since launch | `test_no_one_can_list_every_sentence_anyone_typed`, `test_usernames_are_not_listed_unless_beta_is_switched_on` |
| R9 | No injection path | SQL/FTS5/LIKE are parameterised or escaped. The only subprocess (ffmpeg) runs in list form with `-protocol_whitelist pipe`. Paths are confined. Log lines use `%r`. Key compared as bytes in constant time | audit (§3); `test_a_key_that_is_not_ascii_is_refused_not_a_crash` |
| R10 | The site's pages are hardened | nosniff, X-Frame-Options DENY, Referrer-Policy, Permissions-Policy (microphone only for us), COOP. HSTS (Vercel default) | `vercel.json`; checked against every page and the TWA (§3) |
| R11 | The supply chain cannot slip in code quietly | Actions pinned to commit SHAs. Read-only token. Dependabot for actions, pip and npm. Weekly CVE audit that never blocks a deploy | `.github/`; the pins were matched with `git ls-remote` |
| R12 | Abuse and scraping are bounded without hurting real users or search | Phase 2 (origin gate → real client IP → per-route limits). Robots policy unchanged (§4.4) | phase-2 configs validated by the researcher (§6) |
| R13 | Accounts cannot be taken by typing a name | Phase 2 identity (§5), an owner decision | — |
| R15 | What the privacy page says is what the code does | Each claim was checked against file:line, and the false or missing ones were rewritten | auditor round 3 (§8) |
| R14 | Fast | Pure-ASGI middleware (no `BaseHTTPMiddleware` copy of the body), touching only `http.response.start`. Nothing on the hot path but one contextvar set and one header append | no measurable change in the suite; streams and `FileResponse` pass through untouched (auditor) |

## 2 · System and trust boundaries

```
Browser / Android TWA ──► Vercel edge (static site; /api rewrite) ──► Caddy on the VM (sslip.io:443)
                                                                        └► uvicorn ×2 (127.0.0.1:8000/8001, user ubuntu)
                                                                             └► Groq (LLM + hosted ear), Deepgram, edge-tts, quran.com
GitHub master ──(deploy/sync.sh every 5 min, only ci.yml-green commits)──► VM
```

1. **Client → Vercel.** Nothing the client sends is trusted. Live traffic is same-origin: the TWA loads the
   same Vercel site.
2. **Vercel → origin.** The origin is also reachable directly from the internet. Today nothing proves a
   request came through Vercel (phase 2).
3. **Caddy → uvicorn.** Loopback only. Caddy replaces `X-Forwarded-For` with its peer, which is Vercel's edge.
   So `ratelimit.visitor()` sees Vercel's address, and every visitor shares one bucket (phase 2 fixes this).
4. **App → AI providers.** Every call spends a quota. Model output is untrusted text.
5. **GitHub → VM.** Whoever controls master or a dependency runs code on the VM. The CI gate is the only check.

## 3 · Threat model

Assets, most important first:
- **A1:** learner accounts (progress, shelf, circles; a circle admin reads members' overviews: parents and teachers over children).
- **A2:** the VM and its auto-deploy chain.
- **A3:** AI quotas (Groq, Deepgram).
- **A4:** availability (one 2-CPU VM; parser, fuzzy search, speech).
- **A5:** the built corpora.
- **A6:** trust in AI text shown beside Qur'an and hadith.
- **A7:** the logs themselves (IPs, names).

| Actor | Attack | Today | After phase 1 | Plan |
|---|---|---|---|---|
| T1 curious or griefing user | Sends `X-Tafheem-Profile: someone` to read, change or **delete** that account, or read a circle's children (`identity.py`: username only, by an earlier decision) | open | every account event and unknown-name probe is logged per IP (`login_unknown`) | phase 2 identity (§5) |
| T1 | Lists every username to know whom to impersonate | `/accounts` on | **off** (`beta_list_accounts=False`) | — |
| T1 | Reads every sentence anyone typed via `/api/practice/kept` | open | **closed** | — |
| T2 bulk scraper / AI crawler | Walks `/api/quran`, `/api/hadith`, `/api/dictionary`, Daleel | no limit | logged where it is refused | phase 2: Vercel firewall rules + per-IP limits on costly routes. Open-licence data stays open (§4.4) |
| T3 quota burner | Loops `/morphology/meaning` (uncached), `/dictionary/sentence` (per unique text), `/listen` (hosted ear), `/practice/checked` | no limit | — | phase 2 limits (needs the real IP first) + **owner: Groq spend cap** |
| T4 DoS-lite | Long inputs to parser or fuzzy search; giant uploads; bypasses Vercel to hit the origin | input caps per route | Caddy refuses bodies over 14 MiB before the backend spools them | phase 2 origin gate |
| T5 supply chain | Compromised action tag, npm or PyPI package, or GitHub account | tags unpinned, default token | SHA pins, `contents: read`, Dependabot, weekly audit | owner: secret scanning, push protection, ruleset on master, 2FA |
| T6 prompt injector | Crafts input so the model emits false or offensive text, links or markup | output rendered as **text**: no `dangerouslySetInnerHTML`, no markdown or HTML rendering anywhere (audit). Models get no tools and no secrets | unchanged | phase 3: output checks (§7) |
| T7 log forger | Puts CR/LF or terminal escapes into a logged field | — | JSON-escaped, C0/C1/DEL replaced, capped | — |
| T8 cross-site page | Calls the API from another site with the learner's credentials | `allow_credentials=True` (no cookies existed) | no credentials; narrow methods and headers; CORP same-site | — |

Confirmed non-issues (auditor, file:line in the round-1 notes):
- No cookies, `credentials` or `withCredentials` anywhere.
- `offline.json` never caches a per-learner answer.
- No secrets in git.
- `/docs` is unreachable in production (Caddy routes `/api/*` only).
- FTS5 and LIKE input is escaped.
- The colloquial image path is resolved and contained.

## 4 · Design: options scored

### 4.1 Security log
| Option | Two processes safe | Tamper-resistant | New dependency | Fits house pattern | Chosen |
|---|---|---|---|---|---|
| `RotatingFileHandler` per process | **no** (both rotate the same file) | no | no | yes | |
| `WatchedFileHandler` + logrotate + stderr→journald | yes | journald copy (FSS optional) | no | yes (`journal.py`) | ✔ |
| structlog / loguru | yes | no | yes | no | |
| Ship to a SaaS (Datadog etc.) | yes | yes | yes + cost + PII off-box | no | |

The line format is one JSON object per line: `at, kind, request_id, ip, method, route (template), status`, plus event fields.
Raw usernames stay on account events. The owner is the only reader; names are already public on the
leaderboard; and support needs them. (The researcher proposed an HMAC of the name instead. That was rejected
for now; revisit if anyone else gets log access.)

### 4.2 Middleware
- Chosen: pure ASGI, wrapping `send` only (no `BaseHTTPMiddleware`), so streams and files are untouched.
- The crash answer comes from Starlette's outermost `ServerErrorMiddleware`, after these middlewares have
  unwound. So the request id travels on `scope["state"]`, and `log_crash` adds it plus the API headers
  (`headers.crash_headers`).

### 4.3 Headers
- **API** (`services/core/headers.py`): an inert-document CSP rather than a page CSP, because an API answer is never a page.
- **Site** (`vercel.json`): headers that cannot break anything (auditor checked every page, the recorder and the TWA).
  **CSP for the site is phase 3.** The build injects inline scripts (`vite/bootShell.js` theme hint,
  `vite/preloadFont.js`), so a strict CSP needs build-time hashes and a Report-Only period first.
- **Origin** (`deploy/Caddyfile`): HSTS, `-Server`, the same site headers, header and query filters on the
  access log, and a body cap.

### 4.4 AI scrapers and robots
| Option | Stops bad scrapers | Hurts search / AI answers that cite us | Chosen |
|---|---|---|---|
| `robots.txt Disallow: /api/` | no (they ignore it) | **yes**: Google won't render blocked resources, so `/app` content drops out of the index (researcher, Google docs) | |
| Proof-of-work wall (Anubis) | partly | yes; slows every learner, breaks the TWA's first load | |
| Per-IP limits on costly routes + Vercel firewall rules (bot protection, rate rules) | yes, where it costs us | no | ✔ phase 2 |
| Keep `robots.txt`/`llms.txt` welcoming AI bots (product decision: the content is meant to be found) | — | — | ✔ unchanged |

The open-licence corpora are not secret. The concern is cost and availability, which limits answer.

### 4.5 Supply chain
- **Chosen:** SHA pins; `permissions: contents: read`; Dependabot (grouped, weekly); and `security.yml`
  (pip-audit + `npm audit --omit=dev --audit-level=high`, weekly and on dependency PRs).
- The audit is deliberately **not** in `ci.yml`: `deploy/sync.sh` deploys only green `ci.yml` commits, and a CVE
  published overnight must not freeze unrelated fixes.
- **Rejected:**
  - gitleaks in CI (GitHub's free secret scanning plus push protection does it at the source).
  - Required PR reviews (single maintainer; it would block every deploy).

## 5 · Identity (phase 2, owner decision)

Today sign-up and log-in are by username only. Passphrase and key columns were removed earlier on purpose
(`progress_db.py` migration 3). That is why T1 is open.

| | A status quo | **B device token + recovery code** | C passkeys | D password |
|---|---|---|---|---|
| Stops T1 | no | yes | yes | yes |
| Keeps "no password" | yes | yes | yes | no |
| Friction | none | none on the same device; a code to move devices | biometric tap | type and remember |
| Works in the TWA | yes | yes | unverified in a TWA | yes |
| Effort | 0 | medium | large | medium |

**Recommendation: B.**
1. At sign-up the server mints a 256-bit token and stores only its SHA-256 (a token this random needs no slow hash).
2. The client sends it as `Authorization: Bearer`. CORS adds the header; the test in R7 will demand it.
3. "Move to another phone" shows a one-time recovery code.

Migration is trust-on-first-use: the first request after rollout that names an account without a token
claims it. It is logged (`token_claimed`) so the owner can see and undo a race. C can come later as an
optional upgrade on top of B.

### Phase 2: needs the owner (secrets, server); do it in this order
1. **Origin gate.** Generate `ORIGIN_SECRET` (`openssl rand -hex 32`) and set it in Vercel for Production and
   Preview. On the VM: `/etc/caddy/origin.env` (mode 0600), with `systemctl edit caddy` pointing
   `EnvironmentFile=` at it. Then:
   - Swap in the gate below.
   - Switch `vercel.json` to the routes form below. Vercel compiles that /api route before every `headers`
     entry, so the backend's own headers (phase 1) are what /api keeps.
   - Check a preview deploy: `/api/...?q=x` still reaches the backend with its query, and the bare origin
     answers 403.
2. **Real client IP.** Only once step 1 is live: `ratelimit.visitor()` reads `x-real-ip`, then
   `x-vercel-forwarded-for`, which Vercel sets and Caddy passes through, instead of the first XFF.
   Before the gate anyone could forge it; after it only Vercel can.
3. **Limits.** `PerMinute` on `/morphology/meaning`, `/dictionary/sentence`, `/practice`, `/practice/checked`,
   `/listen`, `/listen/check`, `/progress/signup` and `/progress/login`. Each limit is a config field, like
   `analyze_per_minute`. 429s land in the security log already. Adding limits before step 2 would make all
   learners share one bucket.
4. **Identity B (§5).**
5. **Vercel firewall:** bot protection on; a rate rule on `/api/*` as a coarse outer net.

Caddy gate, validated, and tested live against an echo server: right secret 200; wrong, missing or empty
secret 403; an unset or short secret fails closed with 403; over-size 413; non-/api paths 308 to the site.
```caddy
handle /api/* {
	@weak_secret expression `size("{$ORIGIN_SECRET}") < 32`
	respond @weak_secret 403
	@not_vercel not header X-Origin-Secret "{$ORIGIN_SECRET}"
	respond @not_vercel 403
	request_body {
		max_size 14MiB
	}
	reverse_proxy 127.0.0.1:8000 127.0.0.1:8001 {
		header_up -X-Origin-Secret
		# ...health checks as in deploy/Caddyfile
	}
}
handle {
	redir https://tafheem-app.vercel.app{uri} 308
}
# and in the log filter: request>headers>X-Origin-Secret delete
```
`vercel.json`, schema-checked and compiled with `vercel build`: move the `/api` rewrite into `routes`, which may
sit beside `rewrites`/`headers`/`redirects`.
```json
"routes": [{
  "src": "/api/(.*)",
  "dest": "https://132-145-17-56.sslip.io/api/$1",
  "transforms": [{"type": "request.headers", "op": "set", "target": {"key": "x-origin-secret"},
                  "args": "$ORIGIN_SECRET", "env": ["ORIGIN_SECRET"]}]
}]
```

### Phase 3: hardening that needs a measured rollout
- **Site CSP:** build-time sha256 of the inline scripts; `Content-Security-Policy-Report-Only` for two weeks;
  then enforce.
- **AI output checks** for T6: cap length; refuse output carrying URLs or markup where none is expected; keep
  showing it as text.
- **Service user:** a non-sudo `tafheem` user; stage 2 of the drop-in (`SystemCallFilter`) after a quiet week.
- **Alerting:**
  - a daily `security-report` timer to ntfy;
  - healthchecks.io on `/api/health`;
  - journald Forward Secure Sealing (`journalctl --setup-keys`) so the journald copy of the log is tamper-evident.

## 7 · Owner runbook (one-time)
1. GitHub → Settings → Code security:
   - secret scanning plus **push protection**;
   - CodeQL default setup;
   - a ruleset on `master` (no force-push, no deletion, CI required);
   - 2FA on the account.
2. Groq console: set a monthly **spend limit** on every key in `GROQ_API_KEY` and `LISTENING_GROQ_API_KEYS`.
3. On the VM:
   - check that `.env` has no `BETA_LIST_ACCOUNTS=true`;
   - re-run the install lines of `deploy/setup.sh` for the Caddyfile and logrotate:
     `sudo cp deploy/Caddyfile /etc/caddy/Caddyfile && sudo systemctl reload caddy` and
     `sudo install -m 644 deploy/logrotate.conf /etc/logrotate.d/tafheem`;
   - if `.env` sets `STARTUP_BACKGROUND`, check it still names `guest_sweep` (the default does): without it device
     records idle 180 days are never deleted, which privacy.html promises;
   - set `MaxRetentionSec=90day` in `/etc/systemd/journald.conf` (then `systemctl restart systemd-journald`): the
     security log's journald copy otherwise outlives the file's 90 days;
   - install the updated `deploy/tafheem@.service` (`--no-access-log`: uvicorn's access log put every query string
     into journald, which Caddy's filter never saw) and `sudo systemctl daemon-reload`, then restart one instance at a time;
   - sandbox the service: first warm tts_arabic's model, which downloads into the venv that becomes read-only:
     `venv/bin/python -c "from tts_arabic import get_model; get_model('fastpitch','hifigan',cuda=None)"`.
     Then follow the install and one-instance-at-a-time rollout at the top of `deploy/tafheem-hardening.conf`;
   - run `pip-audit` in the server's venv once, because the server keeps what it installed while
     `security.yml` audits a fresh resolve.
4. Daily or weekly: `bash deploy/security-report.sh`. Lines marked `<-- look` are over a threshold.
5. Phase 2 in the order above.
