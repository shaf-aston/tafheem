# Plan: the security system (web, Android app, server)

Status: phase 1 and phase 2 live (2026-11-12). Phase 3 and the GitHub/Groq console steps of §7 remain for the
owner. Claims close on 2026-12-12 by config.
Lifecycle: requirements → research → threat model → design (options scored) → plan → execute → verify → ship.
Team: lead (threat model, design, execution); **researcher** (primary sources, validated configs with
the real tools: `caddy validate`, `vercel build`, schema checks); **auditor** (read-only attack-surface
review of the code, then of every diff). Each finding below is labelled with its evidence.

## 1 · Requirements

The ask: very high-quality security and security logging, protection against "everything" (injections,
prompt injection, AI scrapers, abuse) on the web, the Android app and the server. Everything must be
done from a CLI, must keep the architecture maintainable, and must keep the app smooth and fast.

How each part is checked:

## 2 · System and trust boundaries

```
Browser / Android TWA ──► Vercel edge (static site; /api rewrite) ──► Caddy on the VM (sslip.io:443)
                                                                        └► uvicorn ×2 (127.0.0.1:8000/8001, user ubuntu)
                                                                             └► Groq (LLM + hosted ear), Deepgram, edge-tts, quran.com
GitHub master ──(deploy/sync.sh every 5 min, only ci.yml-green commits)──► VM
```

1. **Client → Vercel.** Nothing the client sends is trusted. Live traffic is same-origin: the TWA loads the
   same Vercel site.
2. **Vercel → origin.** The origin is also reachable directly from the internet. Today nothing proves a
   request came through Vercel (phase 2).
3. **Caddy → uvicorn.** Loopback only. Caddy replaces `X-Forwarded-For` with its peer, which is Vercel's edge.
   So `ratelimit.visitor()` sees Vercel's address, and every visitor shares one bucket (phase 2 fixes this).
4. **App → AI providers.** Every call spends a quota. Model output is untrusted text.
5. **GitHub → VM.** Whoever controls master or a dependency runs code on the VM. The CI gate is the only check.

## 3 · Threat model

Assets, most important first:
- **A1:** learner accounts (progress, shelf, circles; a circle admin reads members' overviews: parents and teachers over children).
- **A2:** the VM and its auto-deploy chain.
- **A3:** AI quotas (Groq, Deepgram).
- **A4:** availability (one 2-CPU VM; parser, fuzzy search, speech).
- **A5:** the built corpora.
- **A6:** trust in AI text shown beside Qur'an and hadith.
- **A7:** the logs themselves (IPs, names).

| Actor | Attack | Today | After phase 1 | Plan |
|---|---|---|---|---|
| T1 curious or griefing user | Sends `X-Tafheem-Profile: someone` to read, change or **delete** that account, or read a circle's children (`identity.py`: username only, by an earlier decision) | open | every account event and unknown-name probe is logged per IP (`login_unknown`) | **closed by identity B (§5):** a name opens nothing without its device-token cookie. The one exception is an account from before tokens, during the claim window (§5.3) |
| T1 | Lists every username to know whom to impersonate | `/accounts` on | **off** (`beta_list_accounts=False`) | — |

| T3 quota burner | Loops `/morphology/meaning` (uncached), `/dictionary/sentence` (per unique text), `/listen` (hosted ear), `/practice/checked` | no limit | **one AI budget**, charged per call that would reach the model (`ai._ask` → `ratelimit.AI.spend`): 20/min per visitor plus 120/min for everyone, per server process. - No cookies, `credentials` or `withCredentials` anywhere (true at round 1; identity B adds exactly one cookie, §5).
- `offline.json` never caches a per-learner answer.
- No secrets in git.
- `/docs` is unreachable in production (Caddy routes `/api/*` only).
- FTS5 and LIKE input is escaped.
- The colloquial image path is resolved and contained.

## 4 · Design: options scored

### 4.1 Security log
| Option | Two processes safe | Tamper-resistant | New dependency | Fits house pattern | Chosen |
|---|---|---|---|---|---|
| `RotatingFileHandler` per process | **no** (both rotate the same file) | no | no | yes | |
| `WatchedFileHandler` + logrotate + stderr→journald | yes | journald copy (FSS optional) | no | yes (`journal.py`) | ✔ |
| structlog / loguru | yes | no | yes | no | |
| Ship to a SaaS (Datadog etc.) | yes | yes | yes + cost + PII off-box | no | |

The line format is one JSON object per line: `at, kind, request_id, ip, method, route (template), status`, plus event fields.
Raw usernames stay on account events. The owner is the only reader; names are already public on the
leaderboard; and support needs them. (The researcher proposed an HMAC of the name instead. That was rejected
for now; revisit if anyone else gets log access.)

### 4.2 Middleware
- Chosen: pure ASGI, wrapping `send` only (no `BaseHTTPMiddleware`), so streams and files are untouched.
- The crash answer comes from Starlette's outermost `ServerErrorMiddleware`, after these middlewares have
  unwound. So the request id travels on `scope["state"]`, and `log_crash` adds it plus the API headers
  (`headers.crash_headers`).

### 4.3 Headers
- **API** (`services/core/headers.py`): an inert-document CSP rather than a page CSP, because an API answer is never a page.
- **Site** (`vercel.json`): headers that cannot break anything (auditor checked every page, the recorder and the TWA).
  **CSP for the site is phase 3.** The build injects inline scripts (`vite/bootShell.js` theme hint,
  `vite/preloadFont.js`), so a strict CSP needs build-time hashes and a Report-Only period first.
- **Origin** (`deploy/Caddyfile`): HSTS, `-Server`, the same site headers, header and query filters on the
  access log, and a body cap.

### 4.4 AI scrapers and robots
| Option | Stops bad scrapers | Hurts search / AI answers that cite us | Chosen |
|---|---|---|---|
| `robots.txt Disallow: /api/` | no (they ignore it) | **yes**: Google won't render blocked resources, so `/app` content drops out of the index (researcher, Google docs) | |
| Proof-of-work wall (Anubis) | partly | yes; slows every learner, breaks the TWA's first load | |
| Per-IP limits on costly routes + Vercel firewall rules (bot protection, rate rules) | yes, where it costs us | no | ✔ phase 2 |
| Keep `robots.txt`/`llms.txt` welcoming AI bots (product decision: the content is meant to be found) | — | — | ✔ unchanged |

The open-licence corpora are not secret. The concern is cost and availability, which limits answer.

### 4.5 Supply chain
- **Chosen:** SHA pins; `permissions: contents: read`; Dependabot (grouped, weekly); and `security.yml`
  (pip-audit + `npm audit --omit=dev --audit-level=high`, weekly and on dependency PRs).
- The audit is deliberately **not** in `ci.yml`: `deploy/sync.sh` deploys only green `ci.yml` commits, and a CVE
  published overnight must not freeze unrelated fixes.
- **Rejected:**
  - gitleaks in CI (GitHub's free secret scanning plus push protection does it at the source).
  - Required PR reviews (single maintainer; it would block every deploy).

## 5 · Identity (phase 2): device token + recovery code

Before this, sign-up and log-in were by username only. Passphrase and key columns had been removed earlier on
purpose (`progress_db.py` migration 3), which is why T1 was open. The owner chose **B** (the table below) and it
is built: `services/learner/tokens.py`, `backend/identity.py`, `routers/progress.py`, and on the page
`lib/learner/accountCheck.js`, `components/profile/ProfileDialog.jsx` and `RecoveryCode.jsx`.

| | A status quo | **B device token + recovery code** | C passkeys | D password |
|---|---|---|---|---|
| Stops T1 | no | yes | yes | yes |
| Keeps "no password" | yes | yes | yes | no |
| Friction | none | none on the same device; a code to move devices | biometric tap | type and remember |
| Works in the TWA | yes | yes | unverified in a TWA | yes |
| Effort | 0 | medium | large | medium |

C can come later as an optional upgrade on top of B.

### 5.1 What proves a request is the account's
- **Device token:** `tft_` + 256 random bits, one per browser. Only its SHA-256 is stored (a secret this random
  needs no slow hash). It travels in one cookie:
  - `__Host-tafheem`, HttpOnly, Secure, SameSite=Strict, Path=/, 365 days.
  - It is renewed on each `GET /account`, which the page makes on every load.
  - It is swept after 180 idle days with the guest records (`used` is written at most once a day).
  - `COOKIE_SECURE=false` (dev on plain http only) makes it plain `tafheem`; the server warns at startup.
- **Recovery code:** 16 Crockford base32 characters (80 bits), shown as `XXXX-XXXX-XXXX-XXXX`.
  - It is stored as salted scrypt (n=2^14, r=8, p=1), because it is under 112 bits.
  - It is shown once: at sign-up, at a claim, at each log-in with a code, and on asking for a new one.
  - It works once. Using it gives that device a token and the next code (compare-and-set, so two devices
    typing one code at once log in one).
  - Input is forgiving: any case, dashes or spaces, O for 0, I and L for 1.
- **Why a cookie and not `Authorization: Bearer`** (the first draft): no script on the page can read an
  HttpOnly cookie, so XSS cannot carry the token away. The browser keeps it for the PWA, the TWA and every
  tab without code. The researcher checked that it survives the Vercel rewrite and the vite proxy both ways.
  The cost is cross-site request forgery, which §5.2 closes.
- **Strict and lenient routes:**
  - Every route that changes or wipes an account always needs the token: delete, wipe, shelf (read and
    write), the public flag, every circle route, a circle's ranking, new code and log-out.
  - Reads and answers accept an unclaimed account by name while claims are open (§5.3), so a page from
    before tokens keeps working.
  - A missing or foreign token is a 401 with one message, "Log in again on this device", whether or not the
    name exists. An unclaimed name still answers 200 by name while claims are open (log-in too: 200, 403 or
    404), so one visitor may name at most `names_per_minute` (30: a classroom behind one address) different
    usernames a minute without a token, and everyone together `names_all_per_minute` (600), which a forged
    address does not get past (`ratelimit.NAMELESS`; the ceiling is kept apart from the per-visitor table, so
    a flood of addresses evicts visitors, never the ceiling). A browser with its cookie is never counted.
- **Script on the page (XSS):** it can act as the learner while the page is open, but it cannot take the
  token away.
  - The one thing that opens the account from anywhere else is a recovery code. So `POST /recovery` needs the
    current code, or a token minted in the last 15 minutes: a "sudo mode", as for a password change. OWASP's
    Authentication cheat sheet asks for "the current credentials for an account before updating sensitive
    account information" and names no window; GitHub's sudo mode lasts two hours. The 15 minutes is ours.
  - Nothing re-arms that window: a token's mint time is written once, and a log-in by the token already held
    mints nothing (auditor round 10, by repro). A script can still sign the browser up to a throwaway name,
    which logs the learner out until they type their code: a nuisance, not a takeover.
  - Lost the code on an old device? The owner makes one (§7).

### 5.2 Cross-site requests
- SameSite=Strict keeps the cookie off every request another site starts.
- `SameOrigin` (`services/core/headers.py`) is the second lock (OWASP's Fetch Metadata). It refuses with a
  403 any `/api` POST, PUT, PATCH or DELETE whose `Sec-Fetch-Site` is present and is not `same-origin` or
  `none`. Each refusal is audited as `cross_site_write`.
  - `same-site` is refused too. The server's own name is `*.sslip.io`, which is not on the public suffix list,
    so any `x.sslip.io` would count as the same site.
  - The page always calls `/api` on its own origin (the Vercel rewrite, the dev proxy).
  - The researcher ran it in Chrome: XHR, fetch, `sendBeacon` and service-worker requests all send `same-origin`.
  - A request with no `Sec-Fetch-Site` passes. OWASP calls a fallback for those "a mandatory requirement"; ours
    is SameSite=Strict, which the browsers that send no Fetch Metadata (Safari before 16.4) honour. So we follow
    OWASP's design with that fallback, not to the letter.
- A link into the app from Google or WhatsApp arrives without the cookie (Strict). That does not matter: the
  HTML is static, and the page's own `/api` calls right after are same-origin and carry it (tested in Chrome).

### 5.3 Accounts from before tokens: claim on first use
- Existing accounts have no recovery code ("unclaimed").
- **The claim:** while `account_claims_open` is on, the first log-in to one claims it. It gets a token and a
  code. This is a compare-and-set, so one device wins, and it is audited as `token_claimed` with the IP and
  the device family (Android, iPhone and so on, never the user-agent string).
- **When it happens:** the new page claims by itself on load (`accountCheck.js`) and shows the code once. So
  an owner who opens the app in the window claims their own account without doing anything.
- **Only a page that shows the code makes one.** Sign-up and log-in send `shows_code`. A page from before codes
  (a long-open tab, a slow load served from the cache) sends nothing. While claims are open:
  - its sign-up gives that browser the account's token but no code. Being held, the account cannot be claimed
    by anyone else (a claim needs no code *and* no token). The new page, on its next load there, sees
    `has_code: false` and makes the first code (`POST /recovery` takes no proof for the first one) and shows it.
    That call sends `first: true`, so with several tabs open the first tab makes the code and the others get a
    409 instead of replacing the code the first is showing.
    (Round 10 made such accounts unclaimed instead; the auditor showed anyone could then claim them.)
  - its log-in to an unclaimed account claims nothing and drops any token the browser held for another name.
  After claims close the sign-up is the same (token, no code, the new page makes it): minting a code that old
  page never shows would leave the learner with a code they never saw.
- **`beta_list_accounts` must stay off while claims are open:** it would list claimable names, one tap each.
- **A code on screen cannot be dismissed by accident.** The sheet that shows it (sign-up, log-in, claim, new code
  from the profile) has no Esc, no backdrop close and no ✕ until "I have saved it"; a browser that forces it
  shut finds it open again. The claimed code is not kept in react-query's cache. The sheets the header opens by
  itself are rendered into `<body>`, because on a phone the header's profile button is hidden (round 12: the
  claimed code never showed on phones).
- **Unclaimed names are hidden from the global ranking.** It was the one public list of names worth racing for.
  Remaining exposure, accepted for the window:
  - circle co-members still see each other's names;
  - a circle invite answers 404 for an unknown name.
- **Close the window** after about 30 days (§7). After that an unclaimed account opens only with a code the
  owner makes on the server.
- **Precedent, and a caution.** Infrahub let a first SSO log-in adopt a local account of the same name, then
  treated it as a vulnerability: on by default behind a flag, off by default in 1.12, removed in 1.13
  (docs.infrahub.app release notes). Hence a window that closes, an audit line per claim and the owner CLI.
- **Rejected alternative: a "witness" release.** The idea was to first record which devices used a name, and
  only then require tokens. It needs two releases, and an attacker who uses the name in release N is
  witnessed exactly like the owner, so it proves nothing TOFU does not. The researcher agreed.

### 5.4 Disputes and lost codes
`python -m backend.scripts.recovery_code NAME` (on the VM, as `ubuntu`) prints a new code and logs out every
device of the account (`--keep-devices` to keep them). It is audited as `recovery_by_owner`. Logging out
everywhere is the default, so whoever took the account cannot make a new code from a session they still hold.
Settle "that claim was not me" against the `token_claimed` line's IP and device family.

### 5.5 Deliberate deviations and limits
- **We do not claim conformance with NIST SP 800-63B** (rev 4, https://pages.nist.gov/800-63-4/sp800-63b.html).
  The deviations, each deliberate for a no-password learning app:
  - **Session length.** #aal1reauth: an overall reauthentication timeout "SHOULD be no more than 30 days at
    AAL1"; an idle limit is optional. We set 365 days, renewed on use, and an idle expiry of 180 days.
  - **A persistent cookie is the authenticator.** #bindings: "Session secrets that are used as bearer tokens
    for session management SHOULD NOT be persistent", and remember-my-browser cookies "SHALL NOT be used
    instead of authentication" except for AAL2 reauthentication. Ours is exactly that.
  - **scrypt, not PBKDF2.** #lookupver's SHALL ("a suitable password hashing scheme", salt of 32 bits or more)
    is met. #passwordver's SHOULD ("an approved password hashing scheme" from SP 800-132, which approves only
    PBKDF2) is not. scrypt is memory-hard, which PBKDF2 is not; kept on purpose.
  - **No recovery notification.** #savedrecovery: a replacement code "SHALL result in an account recovery
    notification". There is no email or other channel to send one to; the security log has `recovery_new`,
    `login` by code and `token_claimed` lines instead.
  - Met: codes work once and are replaced on use (#lookupver, #savedrecovery), with 80 bits against the 64 asked.
- **Why the session is long.**
  - This is a learning app with no payments or messages, and progress is the asset.
  - Asking for the code monthly would teach learners to store it carelessly or lose their streaks.
  - Revisit if accounts ever hold anything more sensitive.
- **Log-out waits for the server.** The cookie is out of the page's reach, and while it stays, the name alone
  gets back in on that browser. So a log-out the server did not hear keeps the page logged in and says so.
  A page from before codes logs out locally only, which leaves any cookie that browser holds: transitional,
  and gone once the page updates.
- **The answer limit is per account** (a class drilling behind one address is many learners), and per address
  for a guest, whose record is named by a header anyone can change. One address also has its own ceiling
  across all its accounts, `answer_address_per_minute` (1200), so one address with many throwaway names cannot
  use up the everyone-together limit for the rest.
- **A no-code account can be stranded.** One made by an old page has only its browser's token until the new page
  loads there. If that token goes first (that old page logs out, or signs up a second name, which drops the first
  name's token, as on a shared family device), the account has neither token nor code and answers 401: only the
  owner's CLI (§5.4) opens it again. A cleared cookie leaves the token row, so the account stays stuck until the
  idle sweep (180 days) deletes the row, after which it is claimable again if claims are still open. Narrow: it
  needs the old page and no new-page load in between. Before closing claims (§7), list these accounts:
  `SELECT name FROM accounts WHERE recovery IS NULL`, and make codes for any owner who asks.
- **A first code lost on the network is never shown.** If the answer to the first-code call never arrives, the
  account has a code nobody saw; the next load sees `has_code: true` and asks nothing. The owner makes a new one
  (§5.4). Accepted: a 200 lost after the write is rare, and the token still works.
- **A word newly added to words.json** can be refused for the few minutes between Vercel's build and the VM's
  deploy, and a renamed or removed key stops counting toward "learnt". Keep keys stable.
- **Small things left as they are** (auditor round 10): right after a claim the shelf is read back from the
  server, so a setting changed in the seconds before the claim is lost; the load-time check treats any 403
  as "needs the code" (the only other 403, SameOrigin's, cannot happen on a same-origin call).
- **The guest path is out of scope.** `X-Tafheem-Guest` is still a header the page's scripts can read. Sign-up
  with "keep" moves that device's answers to whoever presents the id. The data is low-value and per device.
- **Migration 4** backfills accounts from answers once, so answers orphaned by the old delete-vs-answer race
  come back one last time, as unclaimed accounts. Two processes migrating at the same instant: the second fails

The gate as built (2026-11-12). The secret is not an environment variable: the Caddyfile imports
`/etc/caddy/origin-secret.caddy` (root:caddy 0640, written by `deploy/origin-secret.sh`, which refuses anything
but 64 hex characters), which defines the `origin_gate` snippet. Scored against the first draft, which read
`{$ORIGIN_SECRET}` from an `EnvironmentFile`: there, any reload outside systemd (`caddy reload` from a shell) saw an
empty secret and refused every /api request; here every reload path reads the same file, and a missing file makes
Caddy refuse the new config and keep the old one. The site copy on the VM (`handle {}`) is unchanged.
```caddy
import /etc/caddy/origin-secret.caddy   # (origin_gate) { @not_vercel not header X-Origin-Secret "<64 hex>"; respond @not_vercel 403 }
handle /api/* {
	import origin_gate
	request_body { max_size 14MiB }
	reverse_proxy 127.0.0.1:8000 127.0.0.1:8001 {
		header_up -X-Origin-Secret
		# ...health checks as in deploy/Caddyfile
	}
}
# and in the log filter: request>headers>X-Origin-Secret delete
```
`vercel.json`: the `/api` rewrite moved into `routes` (Vercel's docs: `routes` may sit beside `rewrites`, `headers`,
`redirects` and `trailingSlash`; a transform's `env` is filled in at request time).
```json
"routes": [{
  "src": "/api/(.*)",
  "dest": "https://132-145-17-56.sslip.io/api/$1",
  "transforms": [{"type": "request.headers", "op": "set", "target": {"key": "x-origin-secret"},
                  "args": "$ORIGIN_SECRET", "env": ["ORIGIN_SECRET"]}]
}]
```
